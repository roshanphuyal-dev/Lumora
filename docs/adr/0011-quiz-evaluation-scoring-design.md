# ADR 0011: Quiz Evaluation & Scoring Design

## Status
Accepted

## Context
Quiz generation (`TaskType.QUIZ_GENERATION`, ADR-less but documented in `docs/AI.md`/`docs/AI_WORKFLOWS.md#3`) produces 7 question types: `mcq`/`true_false`/`fill_blank`/`matching` (each has a single verifiable `correct_answer`) and `short_answer`/`long_answer`/`case_study` (each has an open-ended `reference_answer` to grade against, not exact-match). Grading a submitted `QuizAttempt` (`backend/app/models/quiz_attempt.py`) needs a design for: which questions need an AI call at all, how that call is shaped so it doesn't violate the no-AI-call-in-a-loop rule (`.claude/rules/performance.md`), and how a submission's misses turn into `weak_topics` rows for adaptive tutoring (`docs/AI.md#memory--personalization`).

## Decision

**1. Deterministic-vs-AI grading split.** `mcq`/`true_false`/`fill_blank`/`matching` are graded in plain Python (exact string/set comparison against `Question.correct_answer`) — Milestone 7, `backend/` service layer, no AI call, no `task_type`. `short_answer`/`long_answer`/`case_study` are graded by Gemini (`TaskType.QUIZ_GRADING`) since judging semantic equivalence/partial credit against a `reference_answer` requires language understanding a deterministic comparison can't do. Objective types have one unambiguous correct answer — grading them costs money/latency and introduces model non-determinism for a question a Python `==`/set-equality check already answers exactly. Free-text types have no single correct string — "the mitochondria makes energy for the cell" and "it's the powerhouse of the cell, converting nutrients to ATP" must both grade as correct, which requires semantic judgment.

**2. One batched Gemini call per attempt, no OpenCode Zen fallback.** All of an attempt's free-text questions are graded in a single `TaskType.QUIZ_GRADING` call (`ai/orchestrator/schemas.py:QuizGradingRequest.items`, a list), never one call per question — the same no-AI-call-in-a-loop rule that shaped `QUIZ_GENERATION`. This call has no OpenCode Zen fallback, extending the precedent set by `QUIZ_GENERATION`/`STRUCTURED_NOTE_GENERATION` (`docs/AI.md#routing-logic`): OpenCode Zen has no structured-output API, and best-effort-parsing free text into a batched list of `{question_id, score, is_correct, feedback, topic_tag}` results — then matching each back to the right question by id — is even more fragile than parsing a batched question-generation response, because a silently-misparsed or misaligned grade becomes a wrong score persisted as a student's actual grade, not just a malformed study artifact. A hard failure (surfaced to the caller, retried) is strictly preferable to a garbled grade.

**3. Weak-topic derivation.** `TaskType.QUIZ_GRADING`'s Gemini call assigns a `topic_tag` (short free-text string, e.g. `"photosynthesis"`) to every free-text question it grades, correct or not — always populated, not just on a miss, so the aggregation step doesn't need a separate "was this tagged" branch. Deterministic-type questions can also carry a `topic_tag` if `Question` has topic metadata attached at generation time (out of scope for this ADR — Milestone 7 decides how/whether objective questions get a `topic_tag`, e.g. copied from `QuestionItem` generation metadata); the point is that weak-topic tagging is not exclusive to AI-graded questions, it just happens to be assigned *by* the AI call for the questions the AI call already grades. Milestone 7 aggregates every low-scoring `QuizAttemptAnswer.topic_tag` (deterministic misses and free-text partial/no credit alike) into `weak_topics.missed_count`, incrementing the count for that `(user_id, notebook_id, topic)` row (`backend/app/models/weak_topic.py`) rather than replacing it, so weak-topic detection is a running tally across quizzes, not a single-attempt snapshot. This is deliberately a simple missed-count tally, not a separate ML/scoring model — `docs/AI.md#memory--personalization` already treats weak topics as a feed into prompt context, and a dedicated model for this is unwarranted until the simple tally proves insufficient.

**Score scale & `is_correct` convention** (needed for Milestone 7 to match): `QuestionGradeResult.score` is a `float` 0.0–1.0 (`Field(ge=0.0, le=1.0)`), matching the scale Milestone 7's deterministic grading is expected to use for objective types (1.0/0.0, no partial credit there), so an attempt-level score can average both uniformly — confirmed compatible with `QuizAttemptAnswer.score` (`Numeric`, no CHECK constraint, Milestone 5). `is_correct` is a boolean the grading call sets directly (prompt-guided to align with `score >= 0.5`, i.e. "more right than wrong"), not derived from a hardcoded threshold client-side — left as the model's holistic judgment for partial-credit borderline cases, since a strict cutoff would sometimes contradict the qualitative feedback the same call produces for the same answer.

## Alternatives Considered
- **One Gemini call per free-text question** — rejected outright per `.claude/rules/performance.md`; a 5-question attempt with 3 free-text questions would cost 3x the calls/latency of the batched design for no quality benefit (Gemini's context window comfortably fits an attempt's full free-text set).
- **Grade every question type (including objective) through Gemini** — rejected: no accuracy benefit over exact comparison for objective types, strictly worse cost/latency/determinism, and makes attempt grading non-reproducible for questions that don't need judgment.
- **OpenCode Zen best-effort fallback for `QUIZ_GRADING`** — rejected for the same fragility reason as `QUIZ_GENERATION`/`STRUCTURED_NOTE_GENERATION`, with a higher stakes downside here (a bad parse produces a wrong grade shown to the student, not just a malformed study artifact).
- **A separate weak-topic classifier/ML model** — rejected as premature; a per-question `topic_tag` plus a missed-count tally is simple, explainable, and sufficient until proven otherwise. Revisit only if the simple tally demonstrably fails to surface useful weak topics.
- **`is_correct` purely derived from `score >= threshold` client-side** — considered, rejected in favor of having the model set it directly; a fixed threshold applied uniformly can misclassify a genuinely-borderline partial-credit answer where the qualitative judgment ("did they understand it") and the numeric score disagree slightly. The prompt still guides the model toward `>= 0.5` as the expected alignment, so callers can treat it as approximately threshold-derived without the model being mechanically bound to it.

## Tradeoffs
- A quiz attempt with only objective-type questions needs no `QUIZ_GRADING` call at all (fast, free, deterministic); an attempt with any free-text questions has a mandatory Gemini round-trip on submission, adding latency to the submit flow that Milestone 7 must handle asynchronously (`QuizAttemptStatus.GRADING`, already modeled) rather than blocking the request.
- `is_correct` not being a strict function of `score` means the two fields can theoretically diverge from a naive reading (e.g. a UI summing "correct count" vs summing "average score" could disagree slightly) — acceptable since `docs/UI_UX.md`-level display concerns are expected to show both, not just one.
- No fallback means a `QUIZ_GRADING` failure blocks that attempt's grading entirely until retried — consistent with treating a wrong grade as worse than a delayed one, but means Milestone 7 needs a retry/error path (`QuizAttemptStatus` already has room for this via `GRADING` remaining set on failure, resolved by a retry).

## Consequences
- Milestone 7 (`backend/`) implements the deterministic objective-type grading, calls `run_task(TaskType.QUIZ_GRADING, ...)` for the free-text subset of an attempt, and aggregates both into `QuizAttemptAnswer`/`weak_topics` using the score scale and `is_correct` convention fixed here — no re-deriving them.
- Any future new free-text-like question type reuses `TaskType.QUIZ_GRADING`'s batched shape rather than inventing a new per-type grading call, unless its grading contract genuinely doesn't fit `QuestionGradeResult`.
- If deterministic-type `topic_tag` assignment at generation time turns out to need AI judgment (rather than simple metadata), that's a scope change to `QUIZ_GENERATION`'s prompt (`ai/prompts/quiz_generation_v1.py`), not to `QUIZ_GRADING` — grading only tags the questions it grades.
