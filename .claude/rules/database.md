# Database Rules

## Purpose
Schema/migration conventions — applies to SQLAlchemy models and Alembic migrations.

## Responsibilities
System-of-record schema integrity; every schema change is a reviewable, reversible migration.

## Coding Rules
- Every table has an explicit primary key, `created_at`/`updated_at` timestamps, and foreign keys with `ON DELETE` behavior deliberately chosen (not left to default).
- New tables/columns require a corresponding update to `docs/DATABASE.md#core-tables` in the same PR.
- Vector columns (`pgvector`) always scoped with an index appropriate to expected query pattern (`docs/DATABASE.md#indexing-strategy`).

## Conventions
- Table names: plural `snake_case` (`notebooks`, `quiz_attempts`).
- Migration files: one logical change per migration, autogenerate then hand-review.

## Best Practices
- Nullable-first for new columns on existing tables with data (avoid breaking migrations on non-empty tables); tighten to `NOT NULL` in a follow-up migration once backfilled.
- Index every foreign key and every column used in a `WHERE`/`ORDER BY` on a hot path.

## Avoid
- Manual DB edits outside a migration, ever.
- Editing a migration that has already been merged/deployed — write a new one instead.
- Dropping a column/table without a documented rollback note (`docs/DATABASE.md#migration-conventions`).

## Review Checklist
- [ ] Migration autogenerated then hand-reviewed (not blindly trusted).
- [ ] Foreign keys have explicit `ON DELETE` behavior.
- [ ] New/changed tables reflected in `docs/DATABASE.md`.
- [ ] Destructive migrations documented with rollback steps.
- [ ] Vector columns have an appropriate index.
